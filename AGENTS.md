# AGENTS.md

## Роль

Ты Senior Fullstack Engineer и Software Architect.

Ты разрабатываешь local-first desktop-приложение Capacity Planner Desktop для планирования capacity команды разработки.

## Главная цель

Создать надежное desktop-приложение, которое заменяет Excel-таблицу учета capacity команды.

Приложение должно быть:
- локальным;
- быстрым;
- русскоязычным;
- с SQLite-хранилищем;
- с автоматическими расчетами;
- с тестами бизнес-логики.

## Стек

Используй:

- Tauri 2
- React 18
- TypeScript
- Vite
- SQLite через `@tauri-apps/plugin-sql`
- Vitest
- PapaParse
- write-excel-file (выгрузка XLSX, DEC-024) и fflate (синхронное сжатие без Web Worker)
- dayjs
- Zod
- TanStack Table

## Правила архитектуры

- Не размещай бизнес-логику в React-компонентах.
- Все формулы capacity должны быть в `src/domain/capacity/`.
- Прикладные обращения к SQLite должны быть в `src/db/`. Узкий Rust-модуль `src-tauri/src/project_store/` отвечает за проверку, создание, открытие, миграции и закрытие БД; бизнес-формулы и прикладные репозитории в Rust не переносятся.
- Узкий Rust-модуль `src-tauri/src/report_export.rs` только показывает системное окно
  «Сохранить как» и записывает готовые байты отчёта; модель и XLSX строятся в
  `src/export/`. Все IPC-команды регистрируются в `project_store::commands::configure`,
  объявляются в `APP_COMMANDS` в `build.rs` и явно разрешаются в `capabilities/default.json`.
  Фронтенду не выдавать `fs:*` и `dialog:allow-save`.
- `src-tauri/src/macos_app.rs` — меню macOS на русском и защита выхода: Cmd+Q и хук
  `applicationShouldTerminate:` превращают выход в защищённое закрытие главного окна.
  Меню и хук подключаются только в `main.rs` под `cfg(target_os = "macos")`, не в
  `configure()`: тесты вызывают его не с главного потока. Тексты и решения — без cfg,
  с тестами на любой ОС.
- UI-компоненты не должны напрямую выполнять SQL-запросы.
- Все данные должны сохраняться локально.
- Приложение должно работать без интернета.
- Расчеты должны быть детерминированными.
- Изменение состава команды не должно ломать сводки.
- Основной запуск работает с выбранной папкой проекта и `capacity.sqlite`. Не возвращай
  автоматический bootstrap/preload прежней `capacity.db` и не обращайся к ней из нового UI.
  Сохранённые legacy-модули и тесты не означают, что этот поток включён в production.

## Правила UI

- Весь пользовательский интерфейс — на русском языке.
- Не использовать английские названия кнопок и разделов.
- Стиль: светлый, аккуратный, корпоративный.
- Можно использовать легкую тему кабанчиков, но не превращать приложение в мем.
- Таблицы должны быть удобными для пользователя, привыкшего к Excel.
- Не использовать `window.confirm`, `alert`, `prompt`: в WKWebView на macOS они молча не
  работают. Подтверждения — через состояние контроллера и диалог в React.

## Правила расчетов

Решения PO от 2026-09-23, DEC-005–014 в `docs/product/REQUIREMENTS.md`,
заменяют старую базу распределения:

- Распределяются все доступные часы; встречи — отдельная категория. Не уменьшай базу предварительно на 70%/60%.
- Доступные дни рассчитываются по общей пятидневке с праздниками РФ, ручными поправками и датами отсутствий.
- Ставка уменьшает часы пропорционально: 0,5 даёт половину. Норма 8 ч и целодневные отсутствия приняты в MVP; не смешивай ставку и второй вычет тех же часов.
- Часы направления = Доступные часы команды за квартал × Доля направления.
- Доли общие для всей команды в квартале; у задачи одна общая оценка в часах.
- Сопоставление задач с ёмкостью в первой версии — за квартал; у задачи одно направление, резерв направления возможен без задач.
- Даты прихода/ухода внутри квартала не учитываются в первой версии; ручное изменение состава необходимо.
- Каждая команда — отдельный локальный проект; 1–3 команды и 5–20 человек — типичный масштаб, не жёсткий лимит.
- Старые спринты, факт и утилизация не включаются автоматически в новый MVP.

Новые формулы подключены к UI команды, календаря, отсутствий и распределения.
Встроенный календарь покрывает 2026 год; для неизвестного года нужен явный ручной
режим. Сохраняй происхождение календаря и поправки; не пересоздавай календарь при
открытии плана. Оценка задачи `null` не равна `0`; при неполных оценках или долях
остаток предварительный. Малый ненулевой дефицит нельзя скрывать округлением.
Не подменяй открытые вопросы формулами из старого кода.

## Публикация

- Не включать исходные Excel, пользовательские SQLite-файлы, credentials, логи и локальный архив discovery.
- Старый локальный baseline содержит непубликуемые файлы; для удалённой ветки используется отдельная очищенная история.
- Не отправлять `--all`, `--mirror`, архивные ветки или служебные `refs/codex/*`.
- Перед push проверять дерево, историю и точный адрес получателя; отправлять только выбранную ветку.
- Использовать публичную/noreply идентичность коммита, не личный адрес почты из локального baseline.

## Правила тестирования

Обязательно использовать Vitest.

Тестами должны быть покрыты:

- расчет доступных дней;
- отпуска и отсутствия;
- FTE 0.5 / 0.75 / 1;
- отсутствие повторного вычета встреч: 20% от 100 доступных часов = 20 часов;
- расчет часов;
- распределение нагрузки 100%;
- ошибки при сумме нагрузки не 100%;
- сопоставление ёмкости с оценками задач согласно согласованному scope;
- деление на ноль.

Проверки старой производственной загрузки, спринтов, CSV и Plan / Fact относятся
к поддерживаемому старому коду; их наличие не утверждает функции нового MVP.
Не удаляй существующие тесты без отдельной задачи на соответствующее изменение.

## Запреты

Не делай:

- серверную часть;
- облачную авторизацию;
- синхронизацию между пользователями;
- сложный дизайн без необходимости;
- бизнес-формулы внутри React;
- ручные своды по фиксированным строкам как в Excel;
- хардкод месяцев апрель/май/июнь без связи с кварталом.
