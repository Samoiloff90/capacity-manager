# Capacity Planner — требования и discovery

Обновлено: 2026-10-07. Статус: ручной сценарий с задачами реализован; версия 0.3.0 добавляет копирование квартала и число спринтов (DEC-027, DEC-028). Согласована концепция следующей версии — квартального планировщика (DEC-029–DEC-035, QUARTER_PLANNING.md), основа его UX (DEC-036) и решения по поведению (DEC-037–DEC-040); DEC-041 упростил оценку работ: одна полная оценка в часах, шкала размеров исключена из ближайшей версии. Финальный комплект сценариев UX (QUARTER_PLANNING_UX.md) и технический план (../architecture/QUARTER_PLANNING_PLAN.md) согласованы с уточнениями DEC-042–DEC-048. Этапы 1–4 реализованы в ветке `quarter-planner`; промежуточная сборка 0.4.0-alpha.1 для Mac — DEC-049. DEC-050: вставка работ из таблицы (этап 5а), справка по компетенциям и разгрузка вкладки квартала — сборка 0.4.0-alpha.2; чтение .xlsx — этап 5б (../audit/QUARTER_PLANNER_BUILD.md). Направления следующих версий — Kaiten (DEC-051) и ИИ-пилот (DEC-052), пока только исследования (../research/). Выпуск стабильной версии — по команде PO. Пробный Windows ZIP проверен в пределах ../audit/WINDOWS_PORTABLE.md. DEC-023 определил целевые ОС (Windows 10/11 x64, macOS arm64) и уточнил REQ-002: фоновые обращения системного движка допустимы, приложение не передаёт данные команды. На Windows это проверено для версий 0.1.0, 0.2.0 и 0.3.0: маркеров данных в трафике нет, одно соединение движка вне NetLog не проверено по содержимому. На Mac проверен только простой на сервере GitHub. Сборки для macOS и Windows публикуются как релизы GitHub (DEC-025, ../audit/MACOS_BUILD.md); на Mac PO стабильные сборки не проверялись; тестовую 0.4.0-alpha.1 PO кратко проверил сам (DEC-050), весь чек-лист не пройден. Проверка сети — ../audit/NETWORK_CHECK.md. Прототип AppContainer (DEC-022) закрыт. Отчёт XLSX по DEC-024 реализован и проверен на Windows (../audit/REPORT_EXPORT.md).
Источник новых требований: ответы Product Owner после Current State Audit,
включая три раунда интервью о квартальном планировании.
Исходный аудит, анализ рабочего Excel и старые материалы discovery сохранены только
в локальном архиве и не входят в публикацию. Согласованная первая версия и критерии: MVP.md.

## Основной пользовательский сценарий

1. Руководитель описывает свою команду, компетенции и доступность людей.
2. Рассчитывает ёмкость квартала и распределяет её между направлениями работ.
3. Сообщает заинтересованным сторонам, сколько часов команда может предоставить.
4. Вносит задачи и оценки, сопоставляет потребность с выделенными часами.

Оценки задач — плановая потребность. Из этого сценария не следует требование
учёта фактически отработанных часов. Факт и утилизация из старых документов

### CHALLENGE — встречи и коэффициент производственной загрузки

Current idea: в новом примере PO встречи включены в распределение направлений;
старый Excel сначала исключает их коэффициентом 70% (Описание!A1).
Potential problem: если объединить обе схемы, встречи могут быть вычтены дважды.
Alternative: выбрать одну базу — распределять все доступные часы вместе со встречами
или распределять производственные часы после отдельного вычета организационного времени.
Why it may be better: каждая потеря времени учитывается ровно один раз, доли имеют явный знаменатель.
Decision required: NO — вопрос закрыт ответом PO на Q-005, DEC-005.
Выбрано распределение всех доступных часов; встречи учитываются только своей категорией.
Это явное изменение относительно Excel и старых формул прототипа; оно реализовано
в новом расчётном ядре, но ещё не подключено к интерфейсу прототипа.

Дополнительный риск: свободные часы одной компетенции не обязательно компенсируют
дефицит другой. По решению DEC-008 у задачи одна оценка. Поэтому приложение сможет
показывать баланс общих часов, но не сможет достоверно определять дефицит QA/Java
по задачам. Сведения о компетенциях команды сохраняют смысл для обзора доступности;
разбивка задач по компетенциям не добавляется вопреки выбранному упрощению.

## Числовой пример для проверки понимания

Это контрольный пример после расчёта доступности, а не новая модель календаря или FTE.
У команды уже получено 1 000 доступных часов за квартал после отсутствий.

| Направление | Доля | Выделено часов |
| --- | ---: | ---: |
| Продукт 1 | 20% | 200 |
| Продукт 2 | 30% | 300 |
| Баги | 10% | 100 |
| Технический долг | 10% | 100 |
| Встречи | 30% | 300 |
| Итого | 100% | 1 000 |

Дополнительного умножения на 70% нет. Эта часть непосредственно следует из DEC-005/007.

Сценарий с выбранной привязкой задачи к направлению (Q-012, DEC-012):
две задачи продукта 1 с оценками 120 и 100 ч дают потребность 220 ч,
остаток −20 ч и превышение 20 ч; задачи продукта 2 на 240 ч оставляют 60 ч.
Свободные часы продукта 2 сами по себе не увеличивают согласованную долю продукта 1.
Нулевое число задач во встречах не означает, что зарезервированные на них 300 ч
можно автоматически отдать продуктам. Перераспределение требует изменения долей.
Итог по всем задачам не подтверждает выполнимость по компетенциям.

## Предлагаемая последовательность итераций

Последовательность включена в согласованный MVP. Конкретные форматы отчёта,
импорта, внутренняя схема хранения и интерфейс согласуются для своих этапов.

| Шаг | Результат | Проверка результата |
| --- | --- | --- |
| До основной реализации | Согласованный числовой пример и короткая проверка доставки на Windows/macOS | Первый запуск из полученного архива обычным пользователем без сети, установщика, повышения прав и отключения защитных политик; тестовая запись сохраняется после перезапуска. |
| Итерация 1 | Отдельные локальные проекты команд; полный ручной сценарий: команда, календарь и отсутствия → квартальная ёмкость → общие доли направлений → задачи с одной оценкой → остаток/превышение за квартал | Согласованный пример считается правильно без двойного вычета встреч; показан баланс часов по направлениям; состав можно редактировать; проекты изолированы, данные сохраняются и повторно открываются офлайн. |

| Итерация 3 | Импорт JSON/Excel, очередность по частоте реального использования | Сопоставление с выбранными примерами, понятные ошибки и правила повторной загрузки; ошибки старых Excel-формул не становятся расчётными правилами приложения. |

Базовое локальное сохранение входит в первую итерацию. Отложены автоматизация
импорта и специальные сценарии обмена, а не сохранность данных.
Полноценный таск-трекер, интеграции, фактические трудозатраты и синхронизация
не добавляются из предположений; необходимость обсуждается отдельно.

## Ограничения доставки, требующие проверки

Windows: текущему Tauri нужен WebView2. Наличие системного Runtime или поставка
Runtime рядом с приложением должны быть проверены на целевом ПК. Офлайн-установщик
Runtime не равнозначен требованию «без установки». macOS: первая поставка — .app из
GitHub Actions с ad-hoc подписью, без Developer ID и нотаризации (DEC-023, DEC-023a);
подпись разработчика и нотаризация — отдельное решение, если их потребует политика
запуска. Сборка и проверка на раннере — ../audit/MACOS_BUILD.md.
Подготовка выпуска разработчиком может требовать интернета; это отдельно от
отсутствия сетевых обращений готового приложения у пользователя.

Источники технических ограничений:
- [Microsoft WebView2 distribution](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution).
- [Apple notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow).

Способ обхода корпоративных защит не рассматривается. Возможность запуска
под допустимой политикой организации проверяется до обещания portable-доставки.
